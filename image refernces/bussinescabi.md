# QoS Business — план реализации для хакатона

## 1. Цель

Создать простой, полностью демонстрируемый бизнес-сценарий без ручной модерации со стороны QoS.

Бизнес должен самостоятельно:

1. Заполнить форму подключения.
2. Добавить информацию о заведении и меню.
3. Сразу опубликовать заведение в общем клиентском каталоге.
4. Попасть в свой бизнес-кабинет.
5. Получать новые предзаказы.
6. Менять состояние заказов.
7. Управлять меню и доступностью заведения.
8. Смотреть загрузку и распределение заказов в течение дня.

Процесс рассмотрения заявки, звонок менеджера и ручное одобрение для хакатонной версии не нужны.

## 2. Основной пользовательский сценарий бизнеса

```text
Страница «QoS для заведений»
→ форма подключения
→ заполнение данных заведения
→ заполнение меню
→ предпросмотр
→ публикация
→ заведение сразу появляется в общем каталоге
→ бизнес автоматически попадает в кабинет
→ получает и обрабатывает заказы
```

Если бизнес вернётся на платформу позже, он должен войти по указанной почте и паролю либо восстановленной демо-сессии.

## 3. Форма подключения заведения

Форма должна быть не заявкой, а полноценным мастером создания заведения.

### Шаг 1 — основные данные

Обязательные поля:

- название заведения;
- категория заведения;
- контактный номер телефона;
- email;
- адрес;
- точка на карте;
- обложка заведения.

Категории:

- ресторан;
- кафе;
- кофейня;
- бургеры и гриль;
- пицца;
- азиатская кухня;
- донер и fast food;
- десерты;
- другая категория.

Дополнительные полезные поля:

- краткое описание;
- ориентир или комментарий к адресу;
- среднее время приготовления;
- время работы;
- инструкция для самовывоза.

### Шаг 2 — обложка

Бизнес должен:

- загрузить изображение;
- увидеть предпросмотр;
- заменить или удалить изображение;
- получить понятную ошибку при неподдерживаемом формате или слишком большом файле.

Для хакатона можно сохранять изображение в Supabase Storage. Если backend ещё не подключён, допускается временное хранение как Data URL или Object URL, но для полной демонстрации лучше использовать Storage.

### Шаг 3 — меню

До публикации необходимо добавить хотя бы одно блюдо.

Для каждого блюда:

- название;
- категория меню;
- описание;
- цена в тенге;
- изображение;
- примерное время приготовления;
- доступность;
- признак «популярное».

Действия:

- добавить блюдо;
- редактировать;
- удалить;
- временно скрыть;
- изменить порядок;
- создать категории меню.

Для ускорения демонстрации следует добавить кнопку «Заполнить тестовым меню».

### Шаг 4 — график и предзаказы

Бизнес указывает:

- дни работы;
- время открытия и закрытия;
- минимальное время приготовления;
- доступен ли сейчас самовывоз;
- интервалы, на которые можно оформить предзаказ.

### Шаг 5 — предпросмотр и публикация

Перед публикацией бизнес видит карточку заведения так, как её увидит клиент.

Кнопка «Опубликовать заведение» должна:

1. Проверить обязательные поля.
2. Создать бизнес и заведение.
3. Сохранить меню.
4. Сразу установить заведению статус `ACTIVE`.
5. Добавить заведение в общий каталог.
6. Перенаправить пользователя в бизнес-кабинет.

Никаких статусов `На рассмотрении` или `Ожидает менеджера` в MVP не будет.

## 4. Появление заведения в клиентском каталоге

После публикации новое заведение должно сразу отображаться:

- в общем списке на `/`;
- в поиске;
- в выбранной категории;
- на карте, если указаны координаты;
- с созданным бизнесом меню;
- с актуальной обложкой, адресом и временем приготовления.

Каталог должен получать данные из общего хранилища, а не только из статического `mockVenues.ts`.

Статические заведения 2ГИС можно оставить как демонстрационное первоначальное наполнение. Созданные бизнесом заведения должны добавляться к ним.

## 5. Структура бизнес-кабинета

Рекомендуемые разделы:

```text
Обзор
Заказы
Загрузка
Аналитика
Меню
Заведение
Настройки
```

На мобильных устройствах используется нижняя навигация или компактное меню. На ПК — боковая панель.

## 6. Главный экран «Обзор»

После входа бизнес сразу видит рабочее состояние заведения.

### Верхние показатели

- новых заказов;
- готовятся сейчас;
- готовы к выдаче;
- заказов за сегодня;
- сумма заказов за сегодня;
- среднее время приготовления.

### Быстрые действия

- включить или приостановить приём заказов;
- добавить блюдо;
- открыть список заказов;
- отметить блюдо недоступным;
- изменить среднее время приготовления;
- перейти к клиентской карточке заведения.

### Ближайшие заказы

Карточка ближайшего заказа показывает:

- номер;
- код выдачи;
- состав;
- сумму;
- время получения;
- оставшееся время;
- текущий статус.

## 7. Экран текущих заказов

Заказы должны появляться в кабинете без ручного обновления страницы.

Для хакатона возможны два варианта:

- Supabase Realtime — предпочтительный вариант;
- периодический запрос каждые 3–5 секунд — упрощённый резервный вариант.

### Данные заказа

- номер заказа;
- код выдачи;
- время создания;
- запланированное время получения;
- список блюд и количество;
- итоговая сумма;
- бонусный интервал или обычный заказ;
- количество начисляемых бонусов;
- комментарий клиента;
- текущий статус.

### Минимальные статусы

Пользователь просит «готово / не готово», но для понятного процесса рекомендуется четыре состояния:

```text
NEW → PREPARING → READY → PICKED_UP
```

Отображение для бизнеса:

- `NEW` — новый заказ;
- `PREPARING` — не готово, готовится;
- `READY` — готово;
- `PICKED_UP` — выдано.

Дополнительный статус:

- `CANCELLED` — отменено.

Если требуется максимально простой интерфейс, основная кнопка может переключать только `Не готово → Готово`, а принятие и выдача будут отдельными небольшими действиями.

### Действия с заказом

- принять заказ;
- начать приготовление;
- отметить «Готово»;
- подтвердить выдачу по коду;
- отменить заказ;
- указать причину отмены;
- посмотреть историю изменения статуса.

### Уведомления

При поступлении нового заказа:

- появляется визуальный баннер;
- проигрывается короткий звук;
- обновляется счётчик новых заказов;
- заказ подсвечивается до первого просмотра.

## 8. Синхронизация с клиентом

Клиент должен видеть изменения, сделанные бизнесом:

```text
Заказ принят
→ Готовится
→ Готов к выдаче
→ Выдан
```

После статуса `READY` клиент видит крупный код выдачи и сообщение, что можно идти за заказом.

После `PICKED_UP`:

- заказ закрывается;
- если выбран бонусный интервал, бонус начисляется один раз;
- заказ попадает в историю клиента и аналитику бизнеса.

## 9. Аналитика по распределению заказов

Главная аналитическая функция — показать, как заказы распределяются в течение дня.

### Основной график

Столбчатый или линейный график:

- ось X — часы или интервалы по 30 минут;
- ось Y — количество заказов;
- отдельный цвет для обычных и бонусных заказов;
- выделение текущего времени;
- отображение пиковых и незагруженных интервалов.

### Фильтры

- сегодня;
- вчера;
- последние 7 дней;
- произвольная дата.

### Показатели

- всего заказов;
- заказов по часам;
- пиковый интервал;
- самый свободный интервал;
- средний чек;
- общая сумма заказов;
- доля бонусных заказов;
- среднее время приготовления;
- количество отмен;
- популярные блюда.

### Практическая подсказка

Под графиком система может показывать:

> «Наименьшая загрузка сегодня ожидается с 15:00 до 17:00. Можно включить бонусы на этот период».

Для MVP подсказка рассчитывается по минимальному количеству заказов в интервале, без сложного машинного обучения.

## 10. Управление загрузкой и бонусами

Бизнесу нужен простой экран управления спросом.

### Возможности

- увидеть число заказов по временным интервалам;
- указать максимальное количество заказов на интервал;
- закрыть перегруженный интервал;
- включить бонусы на свободный интервал;
- выбрать размер бонуса;
- отключить бонусный интервал.

### Простая модель для хакатона

Для каждого временного интервала хранятся:

- начало и конец;
- лимит заказов;
- текущее количество заказов;
- доступность;
- размер бонуса;
- признак бонусного интервала.

### Состояния интервала

```text
AVAILABLE — доступен
BONUS — свободный интервал с бонусами
BUSY — почти заполнен
FULL — заполнен
CLOSED — закрыт бизнесом
```

Бонус отображается клиенту только у доступных интервалов со статусом `BONUS`.

## 11. Управление меню из кабинета

После публикации бизнес должен иметь возможность:

- добавлять блюда;
- редактировать название, описание и цену;
- менять фотографию;
- скрывать блюдо;
- отмечать блюдо как закончившееся;
- возвращать блюдо в продажу;
- создавать категории;
- менять порядок категорий и блюд;
- просматривать карточку меню глазами клиента.

Изменения должны сразу отражаться в клиентском каталоге.

## 12. Управление заведением

Раздел должен позволять изменить:

- название;
- категорию;
- номер телефона;
- email;
- адрес;
- точку на карте;
- описание;
- обложку;
- график работы;
- время приготовления;
- инструкцию для самовывоза.

Также необходимы переключатели:

- «Заведение открыто»;
- «Принимать предзаказы»;
- «Временно скрыть из каталога».

## 13. Дополнительные полезные функции кабинета

### Стоп-лист

Отдельный быстрый экран, где сотрудник одним нажатием отключает закончившееся блюдо.

### Пауза заказов

Кнопка «Приостановить заказы» с выбором времени:

- 15 минут;
- 30 минут;
- 1 час;
- до ручного включения.

### Оценка готовности

Если кухня перегружена, бизнес может увеличить отображаемое клиенту время приготовления.

### История заказов

- завершённые заказы;
- отменённые заказы;
- поиск по номеру или коду;
- фильтр по дате и статусу.

### Популярные блюда

Рейтинг блюд по количеству заказов и сумме продаж.

### Предпросмотр

Кнопка «Посмотреть как клиент» открывает актуальную карточку заведения и меню.

### Демо-заказ

Кнопка «Создать тестовый заказ» позволяет судьям хакатона сразу увидеть работу кабинета без заполнения клиентской корзины.

### Состояния интерфейса

Необходимо предусмотреть:

- первый вход без заказов;
- загрузку;
- ошибку соединения;
- пустую аналитику;
- отсутствие меню;
- приостановленный приём заказов.

## 14. Упрощённая авторизация

Для хакатона не нужна сложная система сотрудников и ролей.

Достаточно:

- email;
- пароль;
- один владелец на одно заведение;
- автоматический вход после публикации;
- сохранение сессии;
- кнопка выхода.

Если сроки ограничены, можно использовать magic link или демонстрационную авторизацию. Однако кабинет одного заведения не должен открывать данные другого.

## 16. Серверные операции

Минимально необходимы:

```text
POST   /api/business/register
POST   /api/business/login
POST   /api/venues
GET    /api/venues/:id
PATCH  /api/venues/:id
POST   /api/venues/:id/publish
POST   /api/menu/categories
POST   /api/menu/items
PATCH  /api/menu/items/:id
DELETE /api/menu/items/:id
GET    /api/business/orders
PATCH  /api/orders/:id/status
GET    /api/business/analytics
GET    /api/venues/:id/slots
PATCH  /api/slots/:id
```

Критичные серверные проверки:

- бизнес изменяет только своё заведение;
- цена и состав заказа фиксируются при оформлении;
- статус меняется только в допустимом порядке;
- один слот нельзя переполнить параллельными заказами;
- бонус начисляется только один раз после выдачи;
- недоступное блюдо нельзя добавить в новый заказ.

## 18. Этапы реализации

### Этап 1 — данные и хранение

- Подключить Supabase.
- Создать таблицы и Storage.
- Перенести каталог на объединённый источник данных.
- Настроить базовую защиту данных.

Результат: созданные заведения и меню сохраняются после обновления страницы.

### Этап 2 — мастер создания заведения

- Переделать текущую форму `/business`.
- Добавить пошаговое заполнение.
- Реализовать загрузку обложки.
- Добавить конструктор меню.
- Добавить предпросмотр.
- Реализовать немедленную публикацию.

Результат: новое заведение сразу появляется в каталоге.

### Этап 3 — каркас бизнес-кабинета

- Боковая и мобильная навигация.
- Экран обзора.
- Редактирование данных заведения.
- Управление меню и стоп-листом.
- Пауза приёма заказов.

Результат: бизнес самостоятельно управляет своей карточкой.

### Этап 4 — реальные заказы

- Сохранять клиентские заказы в базе.
- Связывать заказ с заведением.
- Показывать новые заказы в кабинете.
- Добавить Realtime или polling.
- Реализовать смену статуса.
- Синхронизировать статус с клиентом.
- Добавить подтверждение выдачи.

Результат: полный заказ проходит от клиента до выдачи.

### Этап 5 — загрузка и бонусы

- Создать временные интервалы.
- Добавить лимит заказов.
- Рассчитывать заполненность.
- Разрешить закрывать интервалы.
- Разрешить включать бонусы на свободное время.
- Показывать бонус клиенту.
- Начислять бонус после выдачи.

Результат: бизнес распределяет заказы в течение дня.

### Этап 6 — аналитика

- График заказов по часам.
- Основные показатели.
- Пиковые и свободные интервалы.
- Обычные и бонусные заказы.
- Популярные блюда.
- Фильтр по датам.

Результат: бизнес видит реальное распределение нагрузки.

### Этап 7 — демонстрационная полировка

- Звуки и уведомления.
- Loading, empty и error states.
- Кнопка тестового заказа.
- Тестовые данные аналитики.
- Адаптивность.
- Полный demo-flow.

## 19. Приоритет разработки

### Обязательно для хакатона

1. Создание заведения без модерации.
2. Мгновенное появление в общем каталоге.
3. Добавление обложки и меню.
4. Редактирование меню.
5. Получение заказов.
6. Статусы «не готово / готово» и выдача.
7. График заказов по времени дня.
8. Управление бонусными интервалами.
9. Пауза заказов и стоп-лист.
10. Адаптивный бизнес-кабинет.

## 20. Полный demo-flow

Демонстрация на хакатоне должна проходить так:

```text
1. Бизнес открывает QoS для заведений.
2. Вводит название, категорию, телефон, email и адрес.
3. Загружает обложку.
4. Добавляет несколько блюд.
5. Нажимает «Опубликовать».
6. Заведение сразу появляется в клиентском каталоге.
7. Клиент открывает это заведение и оформляет заказ.
8. Заказ мгновенно появляется в бизнес-кабинете.
9. Бизнес переводит заказ в «Готовится».
10. Бизнес нажимает «Готово».
11. Клиент видит, что заказ готов.
12. Бизнес подтверждает выдачу.
13. Заказ появляется в аналитике нужного часа.
14. Бизнес видит свободный интервал и включает на него бонусы.
15. Клиент видит бонусное предложение в каталоге.
```

## 21. Критерии готовности

Система считается готовой к демонстрации, если:

- форма не показывает ожидание модерации;
- заведение сохраняется и сразу публикуется;
- после обновления страницы данные не пропадают;
- созданное заведение видно в общем каталоге;
- меню бизнеса открывается у клиента;
- клиентский заказ появляется в нужном кабинете;
- бизнес может отметить заказ неготовым, готовым и выданным;
- клиент видит актуальный статус;
- аналитика показывает заказ в правильном временном интервале;
- бонус можно включить на свободный интервал;
- бонус начисляется только после выдачи;
- кабинет работает на мобильном устройстве и ПК;
- `npm run typecheck` и `npm run build` проходят без ошибок.

## 22. Ограничения хакатонной версии

- Нет ручной модерации заведений.
- Нет проверки юридических документов.
- Один аккаунт управляет одним заведением.
- Нет сложной системы ролей.
- Нет POS-интеграции.
- Нет онлайн-оплаты.
- Нет сложного прогнозирования на основе ML.
- Аналитика строится непосредственно по сохранённым заказам.
- Автоматическая подсказка бонусного времени использует самый свободный интервал.
